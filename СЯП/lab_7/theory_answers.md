## 🏗️ Разбор ВАШЕЙ реализации (самое главное)

Ваш код написан грамотно и полностью соответствует современным требованиям React / TypeScript. Выделим основные "фишки", на которые стоит опираться при защите:

1. **Единый источник истины (Single Source of Truth) через Zod:**
   * У вас создана единая, мастер-схема данных: `RegistrationSchema`. С помощью `z.infer` вы автоматически сгенерировали тип `IFormData`. Если вы добавите поле в Zod, поле автоматически появится в TS-интерфейсе, и TypeScript подсветит ошибки, если вы где-то его забудете.
   * Ваши локальные валидаторы для шагов сделаны изящно: `Step1Schema = RegistrationSchema.pick({ email: true, password: true })`. Это гарантирует, что бизнес-логика (длина пароля, регулярные выражения) не дублируется.

2. **Грамотный State Management через `useReducer`:**
   * Интерфейс состояния `IFormState` содержит все необходимое: текущий шаг, сами данные, объект ошибок и статусы отправки.
   * `TFormAction` (Discriminated Union) жестко типизирует возможные действия (обновление конкретного поля, шаги вперед/назад, ошибки). 
   * Важно: в Action-типе "UPDATE_FIELD" разработчик сразу очищает ошибку для редактируемого поля `errors: { ...state.errors, [action.field]: undefined }`. Это отличная практика UX (как только начинаешь исправлять ошибку — красная надпись пропадает).

3. **Безопасная валидация без "крашей":**
   * Вы использовали встроенный метод `.safeParse()`. Благодаря этому при вводе некорректных данных программа не зависает и не выбрасывает Runtime-ошибки в консоль. Сборка ошибок красиво мапится в `IFormState['errors']`.

## 🎯 Ответы на контрольные вопросы

### 1. Опиши четыре роли паттерна Flux. Какая из них является «центральным узлом», рассылающим уведомления?
Паттерн Flux включает в себя четыре роли:
* **Action (Событие/Команда)** — объект, описывающий намерение (что-то произошло). Обязательно имеет тип и может нести полезную нагрузку (payload).
* **Dispatcher (Диспетчер)** — центральный узел. Он принимает Actions и рассылает (диспатчит) их по всем подключенным хранилищам.
* **Store (Хранилище)** — содержит данные (стейт) и логику их обработки. Обновляется только под воздействием пришедших от диспетчера экшенов.
* **View (Представление)** — React-компоненты. Они читают стор для отображения интерфейса и создают новые экшены (например, по клику), отправляя их в диспетчер.
> **Центральный узел** пересылки сообщений — **Dispatcher.**

### 2. Что означает принцип «однонаправленного потока данных»? Может ли Store во Flux быть изменен напрямую из View?
Однонаправленный поток данных (Unidirectional data flow) означает, что данные в приложении всегда движутся по строгому циклу:
**Action -> Dispatcher -> Store -> View -> *(новое действие пользователя)* -> Action...**
Напрямую изменить Store из View **нельзя**. View не имеет доступа к методам записи в Store; он может лишь инициировать отправку Action, который запросит изменение данных у Store. За счет этого обеспечивается полная предсказуемость логики.

### 3. Назови «три кита» useReducer. Без каких составляющих работа этого хука невозможна?
Чтобы хук `useReducer` работал, ему обязательно нужны 3 вещи:
1. **Reducer** функция — логика того, *как* меняются данные в зависимости от экшенов.
2. **InitialState** — начальное, стартовое состояние.
3. Функция **dispatch** (которую возвращает хук) — она используется для «заброса» экшенов внутрь Reducer функции для инициирования изменения состояния.

### 4. Что такое Reducer с точки зрения функционального программирования? Почему важно, чтобы это была «чистая функция»?
Редьюсер — это функция, которая на основе текущего состояния (State) и полученного воздействия (Action) возвращает абсолютно новое состояние. Сигнатура: `(state, action) => newState`.
**Важность "чистоты":** Чистая функция не мутирует (не меняет напрямую) входной параметр `state` (в ней нет вещей вроде `state.value = 1`), у неё нет побочных эффектов (запросы к API, таймауты лежат вне редьюсера) и для одинаковых входных данных она всегда вернет одинаковый результат. Если Reducer мутирует state, React просто не узнает о том, что данные изменились, так как ссылка на объект `state` в ОЗУ останется прежней — интерфейс (компонент) не перерисуется!

### 5. Какую роль выполняет функция dispatch?
Она доставляет объект действия (Action) внутрь Reducer'а. `dispatch` сообщает реакту: «произошло действие, выполни функцию-редьюсер, возьми тот state, который она вернёт, и обнови компонент».

### 6. Как типизация Action в TypeScript помогает избежать ошибок при «бомбардировке» редьюсера командами?
Использование Union (размеченных объединений) (например, `type TFormAction = { type: 'NEXT' } | { type: 'UPDATE_FIELD', field: string, value: string }`) не даёт разработчику:
1. Передать несуществующий `type` в параметр Dispatch.
2. Забыть передать нужные payload данные (TypeScript подсветит, что для экшена UPDATE_FIELD не хватает параметра `field`).
3. В самом редьюсере в операторе `switch` TypeScript «сужает» типы и обеспечивает автокомплит конкретных полей, известных только этому конкретному action (Type Guard).

### 7. Как редьюсер обрабатывает экшены, тип которых ему неизвестен (ветка default)?
В ветке `default` редьюсер обязан возвращать текущее состояние `return state;` без каких-либо изменений. Это гарантирует, что если в редьюсер прилетит неопознанный экшен (что бывает крайне редко в TS, но возможно в больших Flux-приложениях), стейт не обнулится, и приложение не сломается.

### 8. Чем метод .safeParse() отличается от .parse() и в каких случаях какой использовать?
* `.parse(data)` попытается отвалидировать объект. Если возникнут ошибки (например, пароль короткий), он вбросит Runtime-Исключение (throw Error). Приложение «крашнется», если не обернуть этот код в блок `try/catch`. Его используют там, где прилет невалидных данных не предполагается концептуально (например, сломалось API) и работа дальше невозможна.
* `.safeParse(data)` не выбрасывает ошибок. Вместо этого он возвращает объект-результат. Либо `{ success: true, data: T }`, либо `{ success: false, error: ZodError }`. Идеально подходит для валидации форм, где пользовательские ошибки ввода — это не системный сбой, а ожидаемый штатный процесс.

### 9. Как с помощью Zod создать тип на основе существующей схемы без ручного написания interface?
Для этого предусмотрен дженерик-метод:
`type MyType = z.infer<typeof MySchema>;`
Именно его вы использовали во фразе: `type IFormData = z.infer<typeof RegistrationSchema>;`. Он конвертирует описанные вами runtime-правила Zod в полноценный TypeScript-тип на этапе компиляции. Это и есть принцип *Single Source of Truth*.

### 10. Зачем использовать .pick() или .partial() при создании схем для API?
* **.pick()** позволяет создавать более точечные схемы (например, только для 1 шага формы) из одной глобальной «мега-схемы». Чтобы на 1-м шаге валидировались только почта и пароль, а об отсутствии `city` Zod не ругался.
* **.partial()** делает все поля схемы опциональными. Это крайне полезно при отправке PATCH-запросов на сервер (изменение только части данных), когда можно отправить либо только имя, либо только город. В таком случае нам не нужно заставлять базу или апи валидировать весь объект с обязательными полями.

## 🎯 Ответы на контрольные вопросы (Лабораторная №7)

### 1. В чем концептуальное отличие useReducer от useState? В каких случаях предпочтительнее использовать первый?
`useState` управляет простым состоянием (число, строка, простой объект). Логика обновления состояния при `useState` размазана по компоненту (в обработчиках). 
`useReducer` выносит логику в отдельную чистую функцию (редьюсер). Он получает команды (actions) и централизованно обновляет стейт. 
Его предпочтительно использовать, когда:
- Состояние представляет собой сложный объект со множеством полей (например, список товаров, статусы загрузки и ошибки заодно).
- Следующее состояние сильно зависит от предыдущего.
- Существует много разных видов воздействий на стейт (CRUD операции), чтобы не писать множество `setSomething` в компоненте.

### 2. Какую роль выполняет функция dispatch? Почему мы передаем в нее объект с полем type?
 Функция `dispatch` служит для отправки «команд» (actions) внутрь `useReducer`. 
 Мы передаем объект с обязательным полем `type`, потому что редьюсеру необходимо знать **что именно** произошло (какое действие выполнить). В конструкции `switch(action.type)` редьюсер определяет логику обновления, а дополнительные поля объекта (payload) предоставляют данные для этого обновления.

### 3. Почему запрос за списком товаров (GET) необходимо оборачивать в хук useEffect? Что произойдет, если вызвать fetch прямо в теле компонента? 
Рендер компонента в React (его тело) должен быть чистым. Если вызвать `fetch` напрямую в теле компонента, запрос будет отправляться при каждом, даже самом малейшем перерендере компонента (например, при вводе текста в инпут). При получении ответа мы поменяли бы стейт списка товаров, что вызвало бы новый рендер компонента... который снова вызвал бы `fetch`. Возникнет бесконечный цикл (infinite loop) запросов на бэкенд. `useEffect` позволяет выполнить этот код ровно один раз (с пустым массивом зависимостей `[]`) после первого монтирования.

### 4. Объясните логику обновления стейта при удалении (DELETE) товара. Почему мы сначала ждем ответа от сервера, а затем вызываем dispatch с методом .filter()? 
Такой подход называется пессимистичным обновлением (Pessimistic UI). Мы сначала отправляем команду бэкенду удалить данные в базе. И только если сервер отвечает успехом (`response.ok`), мы локально удаляем товар из стейта массива с помощью `.filter(item => item.id !== id)`, чтобы перерисовать UI. Это гарантирует, что интерфейс всегда согласован с сервером. Если бы мы обновили стейт до запроса (Optimistic UI) и сервер упал с ошибкой, в интерфейсе товар исчез бы, но по факту остался бы в базе.

### 5. В чем разница между POST и PUT запросами в контексте добавления и изменения товара?
* **POST** используется для создания новой сущности, когда мы не знаем заранее ее идентификатор (его присваивает база данных).
* **PUT** (и PATCH) используется для полного обновления уже существующей сущности. В таком запросе мы передаем идентификатор (в URL или в теле), чтобы сервер знал, какую именно запись перезаписать предоставленными данными.

### 6. Что возвращает метод ProductSchema.safeParse(data) в случае успеха и в случае провала валидации? 
В случае успеха он возвращает объект вида: `{ success: true, data: T }`, где `data` — это отвалидированные и, при необходимости, преобразованные данные (прошедшие через Zod-схему).
В случае провала он не выбрасывает исключений (Error), а возвращает `{ success: false, error: ZodError }`. Из объекта ошибки можно извлечь понятные текстовые сообщения с помощью метода `.flatten()`.

### 7. Что делает конструкция z.infer<typeof ProductSchema> и какую проблему двойного написания кода она решает?
Она автоматически генерирует TypeScript интерфейс (на этапе компиляции) на основе описанной логически Zod-схемы (которая работает на этапе исполнения). Это решает проблему "двойного источника истины" (DRY), когда разработчику приходилось бы писать и `interface IProduct`, и валидатор `z.object()`, и вручную следить за их синхронизацией при добавлении новых полей.

### 8. Как приложение «понимает», что пользователь авторизован, если он закрыл вкладку и открыл ее заново через час? Опишите механизм восстановления сессии.
В браузере существует `localStorage` (длительное локальное хранилище), данные в котором не стираются при закрытии вкладки. 
При первом открытии страницы (при загрузке компонента `AuthProvider`) срабатывает `useEffect`, который читает `localStorage.getItem("authUser")`. Если данные там есть, они конвертируются обратно в объект (`JSON.parse`) и загружаются в state реакта `user`. В результате `isAuthenticated` становится `true`, и приложение сразу пускает пользователя в CatalogPage. При нажатии «Выйти» мы очищаем `localStorage`, уничтожая сохраненную сессию.
